Context

Scaling without a foundation

Vajro is a mobile app builder for Shopify merchants — a platform with multiple product surfaces: a dashboard, a live preview app, onboarding flows, and a mobile SDK builder. By 2021, three designers were working across these surfaces with no shared component library, inconsistent token usage, and deeply divergent visual styles.

The engineering team was rebuilding components from scratch for every new feature. A button styled one way in onboarding looked different in the dashboard. Developers frequently raised "design inconsistency" issues in QA — a process friction that slowed every sprint.

The Mandate

Build the system designers and developers both use

The common failure mode for design systems is that they're built for designers and ignored by engineers — or vice versa. My mandate was explicit: the system had to be the single source of truth for both. This meant co-designing the token structure with the frontend lead, naming conventions aligned to code variables, and documentation written for both audiences.

Success was defined as: fewer design inconsistency issues in QA, faster onboarding for new designers, and a handoff process where engineers didn't have to ask questions.

Starting Point

The "before" state

Build Process

Token-first, component-second

01

Audit + Component Inventory

Audited all existing Figma files and the codebase. Catalogued 340 unique UI elements across all surfaces. Grouped them by semantic function (not visual appearance) to identify the canonical component set. Reduced 340 elements to 80 core components with variant states.

02

Design Token Architecture

Designed a three-tier token system: primitive tokens (raw values: #2563EB), semantic tokens (--color-primary-600), and component tokens (--button-background). Co-authored the naming convention with the frontend lead to ensure tokens mapped directly to CSS custom properties. Used Figma Tokens (now Variables) for live token management.

03

Component Library Build

Built 80+ components across 6 categories: Foundations (typography, colour, spacing, elevation), Atoms (buttons, inputs, badges, tags), Molecules (cards, modals, tooltips, dropdowns), Organisms (tables, nav, sidebars), Patterns (empty states, loaders, error states), and Templates (page layouts). Every component includes all variant states: default, hover, focus, disabled, error.

04

Documentation + Storybook Alignment

Wrote documentation for every component: usage guidelines, do/don't examples, accessibility notes, and code props reference. Worked with engineering to ensure every Figma component had a corresponding Storybook story — making the system a two-way mirror between design and code.

05

Adoption Strategy

Ran a 3-session onboarding workshop for the design team and a separate session for frontend engineers. Created a "migration guide" for updating existing screens to use system components. Tracked adoption via Figma analytics — within 6 weeks, 90% of new design work used system components exclusively.

Technical Design

The token pyramid

Primitives
Raw values — #2563EB, 16px, 400ms. No semantic meaning. Never used directly in components.
Semantic
Meaningful aliases — --color-primary, --spacing-md, --radius-sm. Used in component definitions.
Component
Component-scoped — --button-bg, --input-border. Enables theming without touching component code.

Strategic Lens

Design systems are people problems

The technical work of building the system was the easy part. The hard part was adoption — convincing designers already mid-sprint to pause and migrate their work, and convincing engineers to switch from their custom component library to the new system.

The lesson: a design system is a product. It has users (designers and developers), it needs a go-to-market strategy (onboarding workshops, migration guides), and it needs ongoing maintenance to stay relevant. The 6-week build was the launch — the real work was the 6 months of iteration that followed.

This experience is why I believe every design team of 3+ people needs a dedicated design system owner — not as a side project, but as a primary responsibility. The compounding returns on design system investment are among the highest in any design discipline.
